# 报告统一样式与模板拆分复盘

**复盘日期**：2026-08-13  
**项目**：yuntu-industry-content-rankings-analysis  
**复盘范围**：报告从单体渲染逻辑向 `yuntu_report.py`、`final-report-template.html`、`unified-report.css`、`unified-report.js` 四层拆分的全过程，以及随后出现的报告布局和内容结构异常。

## 1. 结论摘要

本次问题不是单个 CSS 属性或单个模板占位符错误，而是一次高耦合报告渲染系统的边界迁移。原报告的结构、数据和样式虽然集中在 Python 中，但经过多轮业务调整已经形成隐含契约；拆分时只抽取了文件，没有先把这些契约显式化。因此，视觉样式、HTML 骨架、数据渲染和浏览器交互之间出现了重复控制、优先级覆盖和结构假设不一致。

最明显的用户影响包括：

- 人群洞察中年龄分布和性别分布由原本的左右布局变成上下布局。
- 单素材深度分析的卡片、标签、图片和分析信息层级被破坏。
- 报告标题、章节说明、来源说明等内容在模板和 Python 两处重复维护，修改后容易出现缺失或口径不一致。
- 多次“修复”改变了报告结构，造成回退范围难以判断。
- 验证主要证明“字符串存在、测试通过、文件可生成”，没有证明真实报告在关键视口和关键章节上保持视觉等价。

`19bc37048994f26f9f386837ea77adeba49d089c`（`新增人群洞察看板`）是统一资产拆分提交 `8c110b3` 之前的可恢复基线；保护分支 `backup-before-report-rollback-20260812` 保留了 `e3cd7e2` 状态。复盘编写时的当前分支 HEAD 为 `b11f12e`（`优化单素材深度分析体验`），仍包含统一资产拆分及其后的变更，因此不能将当前代码表述为已恢复到 `19bc370`。

## 3. 原始目标与实际变化

### 3.1 原始目标

希望将报告职责拆成四层：

1. `yuntu_report.py`：数据加工、业务规则和 HTML 数据片段渲染。
2. `final-report-template.html`：页面骨架、章节顺序和唯一资源入口。
3. `unified-report.css`：统一视觉样式。
4. `unified-report.js`：Tab、图表、高光预览、分页、秒级趋势等交互。

该目标本身合理，能够减少 Python 中的大块样式字符串，并支持后续复用。但它只有在“数据结构和 DOM 结构先稳定、样式只消费稳定 DOM、交互只依赖稳定 data 属性”的前提下成立。

### 3.2 实际变化

`8c110b3` 同时改变了四类契约：

- 模板从 `$style` 单一样式入口变成 `$style`、`$unified_style`、`$unified_script` 多入口。
- Python 增加了资源读取、模板占位符计数和统一 class 注入。
- 模板删除或移动了原有标题、来源和章节说明位置。
- 新 CSS/JS 对现有 `.pie-layout`、`.audience-pie-layout`、`.brand-panel`、图片容器和 section 结构增加了全局规则。

这不是“只抽离样式和脚本”，而是一次模板结构、class 命名、资源注入和内容归属的联合迁移；但迁移没有配套 DOM 契约和视觉基线。

## 4. 根因分析

### 4.1 一阶反思：流程层

**问题描述**：拆分后报告生成成功，但真实页面结构错误，尤其是人群图表左右关系和单素材深度分析格式。

**发生阶段**：主要发生在实现阶段和实现后的验证/评审阶段。

**根因定位**：

- 先改架构边界，后继续叠加业务展示变更，没有设置“拆分冻结窗口”。
- 没有在拆分前导出并锁定关键章节的 DOM 快照、计算样式和截图基线。
- 测试验证了模板字符串、资源内联和部分 class，却没有验证布局方向、网格列数、卡片层级、图片比例等用户可见契约。
- 真实数据链路验证与单元测试验证的是不同输入契约；旧 fact pack、诊断分析数据和高光数据之间存在版本差异，却没有在渲染入口统一校验。
- 回退判断以“最近提交”或“已通过测试”为依据，未第一时间回到拆分提交的父提交。

**流程缺口**：缺少“结构迁移前置审计”和“真实成品等价性门禁”。

### 4.2 二阶反思：设计抽象层

当前设计存在明显 footgun：

- 同一页面的样式既由 Python `$style` 产生，又由统一 CSS 产生，存在 CSS 双源和优先级竞争。
- 模板同时承担内容编排和视觉 class 约定，Python 又通过字符串拼接决定大量 DOM 结构，边界不是真正隔离。
- 资源以内联方式注入，解决了“成品依赖外部文件”，但掩盖了资源版本和 DOM 版本必须成对匹配的问题。
- class 不是显式 schema；改变一个 class、包裹层或元素顺序，可能不会触发 Python 异常，却会静默改变布局。
- 报告入口同时接受模型分析 JSON 和 fact pack，缺少明确版本化的渲染输入合同。

**更优抽象方向**：

1. 先定义版本化 `ReportViewModel` 和 DOM contract，再让模板只负责骨架。
2. 每个视觉组件只有一个样式源；Python 不再生成 CSS，模板也不再保留重复的内联样式。
3. 交互通过稳定的 `data-*` 属性绑定，不依赖脆弱的层级选择器。
4. 将“布局结构”和“业务内容”分开测试：结构测试检查 DOM，视觉测试检查截图/计算样式，数据测试检查 ViewModel。
5. 统一报告资源使用 manifest（CSS/JS/模板同一版本号），资源版本不匹配时直接失败。

**架构债标记**：是。现有报告渲染器仍是字符串拼接型渲染器，适合短期保守维护，不适合继续进行大范围结构迁移。

### 4.3 三阶反思：机制兜底与主动审查

| 可预期偏差 | 主动检测 | 独立审查 | 失败状态 |
|---|---|---|---|
| CSS 覆盖导致左右布局变上下布局 | 断言关键容器 `grid-template-columns`、`flex-direction` 和宽度 | 视觉回归审查 | `pending_visual_review` |
| 单素材 DOM 包裹层变化 | DOM contract 检查关键 class、节点数量和嵌套关系 | code review + 章节抽样 | `blocked_dom_contract` |
| 模板、CSS、JS 版本不一致 | manifest 版本匹配断言 | 发布前审查 | `blocked_asset_version_mismatch` |
| fact pack 与分析 JSON 口径不一致 | 输入 schema、字段计数和高光可用性断言 | 数据链路复核 | `blocked_input_contract` |
| 测试通过但真实页面变形 | 固定数据生成 1440x1000、390x844 基线截图并做差异阈值 | 独立视觉验收 | `pending_visual_review` |

至少需要两个独立证据源：一是渲染后的 DOM/计算样式断言，二是真实报告截图或人工视觉审查；单元测试或 HTML 文本搜索不能单独作为完成证据。

## 5. 影响范围

### 用户可见影响

- 人群洞察信息层级改变，左右对比关系被破坏。
- 单素材深度分析不再保持原有阅读顺序和视觉分组。
- 报告章节说明和来源信息出现删减，读者上下文变弱。
- 反复生成的报告可能因为输入目录和资源版本不同而表现不一致。

### 工程影响

- 回退成本增加：必须识别“拆分提交”而不是只回退最后一轮业务修补。
- 真实报告目录产生多个副本，增加了用户打开错误产物的概率。
- 被忽略的 `assets/report/unified-report.css/js` 文件在回退后仍可能留在工作区，容易造成“代码已回退但资产仍被误用”的误判。

## 6. 哪些做法是有效的

- 通过 Git 提交边界最终定位到 `8c110b3`，并回退到其父提交 `19bc370`，避免继续在错误架构上打补丁。
- 创建保护分支后再回退，保留了恢复路径。
- 对真实数据执行过全链路生成，问题在最终产物中暴露，而不是只停留在单元测试。
- 后续报告目录清理采用可恢复方式，未删除原始数据、highlights、normalized 等源资产。

## 7. 验证缺口

本次拆分提交增加了资源存在性、模板占位符和字符串结构测试，但缺少：

- 人群图表左右布局的断言。
- 单素材深度分析的 DOM 快照或截图基线。
- 模板渲染前后的结构 diff。
- 真实 fact pack 与分析 JSON 的版本/字段合同检查。
- 资源版本一致性和回退后残留资产检查。
- 桌面与移动视口的视觉回归门禁。

因此“测试通过”与“报告视觉正确”之间存在不可接受的证据断层。

## 8. 后续治理建议

### 立即执行

1. 以 `19bc370` 作为保守生产基线，冻结四层拆分相关改动。
2. 清晰标记 `assets/report/unified-report.css/js` 为实验资产；在确认不再使用后再清理，避免误删用户数据。
3. 报告生成只保留一个规范输出目录 `final-report/`，其他副本使用 Trash 或明确归档标识。
4. 在继续任何样式调整前，先补一份“当前正确报告”的桌面和移动截图基线。

### 后续重构前置条件

1. 定义 `ReportViewModel v1`，明确分析 JSON、fact pack、高光帧和素材详情的来源、必填字段与降级规则。
2. 定义 DOM contract：每个章节的根节点、关键 class、布局方向、卡片数量、图片容器和交互 data 属性。
3. 选择单一 CSS 来源，禁止 Python 与外部 CSS 同时控制同一组件。
4. 采用小步迁移：一次只迁移一个组件，先做视觉等价，再迁移下一个组件。
5. 每一步都必须执行：单元测试、结构断言、真实数据生成、双视口截图、独立审查。
6. 只有在所有关键章节视觉等价后，才允许删除旧实现。

### 完成态门禁

后续任何报告样式或模板任务，除非同时满足以下条件，否则只能标记为“待视觉审查”：

- Git diff 只包含批准范围。
- 输入契约校验通过。
- 关键 DOM contract 全部通过。
- 桌面/移动真实报告截图与基线在阈值内。
- 人群洞察和单素材深度分析由人工抽样确认。
- 输出目录只保留一份规范 `final-report`。

## 9. 最终状态

本复盘不引入新的代码优化，也不改变当前分支。`19bc370` 已被确认是拆分前基线，但复盘编写时 HEAD 为 `b11f12e`，不能将工作区误报为已停留在该基线。后续若再次推进通用化，应以“先稳定数据和 DOM 契约、再渐进迁移视觉和交互”为前提，并在每一步保留可回退提交和真实报告基线。
