# 云图真实完整流程优化项总结

日期：2026-08-09
背景：基于 `2026-07-28 ~ 2026-08-02` 这次真实技能执行复盘，整理后续需要优化的流程、代码和报告生成机制。

## 一、优先级结论

当前最需要优先优化的是：

```text
P0：报告正文分析内容不能只由本地程序化模板生成，必须接入对话中的模型分析步骤。
```

原因：

- 当前 `prepare-analysis` 只生成事实包和分析提示。
- 当前项目没有自动调用对话模型生成 `yuntu-ai-analysis.json` 的完整链路。
- 本次为了完成报告渲染，`yuntu-ai-analysis.json` 是基于事实包用本地脚本程序化生成的。
- 这种方式可以通过渲染器结构校验，但业务洞察表达会偏模板化，缺少真正的综合判断、取舍和自然语言归纳。
- 用户期待的“技能真实完整流程”应包含：RPA 抓取 → 事实包 → 对话模型分析 → 结构化分析 JSON → 报告渲染，而不是跳过模型分析。

因此，这一项应排在最高优先级。

## 二、P0 优化项：补齐模型分析生成链路

### 当前问题

当前流程中：

```text
prepare-analysis
  -> yuntu-analysis-data.json
  -> yuntu-analysis-prompt.md
```

之后缺少一个稳定步骤：

```text
对话模型读取事实包和提示词
  -> 生成 yuntu-ai-analysis.json
```

结果是执行时只能临时用脚本从事实包拼出 `yuntu-ai-analysis.json`。

这会带来几个问题：

- 报告文字容易变成指标拼接，不是真正的商业分析。
- TOP 素材组合结论、人群洞察、品牌差异总结的表达不够像“顾问式结论”。
- 模型没有充分使用上下文中的设计要求和用户反馈。
- “真实完整流程”的定义不够闭合。

### 优化目标

形成明确、可重复、可校验的模型分析步骤：

```text
RPA fetch
  -> prepare-analysis
  -> model-analysis
  -> render-report
  -> validate-report
```

其中 `model-analysis` 需要产出：

```text
diagnostic-analysis/yuntu-ai-analysis.json
```

并满足渲染器要求：

- 必须包含 `topMaterialCombination`
- 必须包含 `rankingOverview`
- 必须包含 `materialComparison`
- 必须包含 `materialDiagnoses`
- 必须包含 `competitorPatterns`
- 必须包含 `opportunityMap`
- 必须包含 `experimentMatrix`
- 每个结论必须有 `summary`
- 前五个章节必须有 `evidence`
- 前五个章节必须有 `material_id` 或 `material_ids`
- 不得把 `evidence` 原文渲染到报告正文
- 不得出现“查看数据依据”

### 建议实现方式

新增一个明确命令或流程步骤，例如：

```bash
python scripts/rpa_connector.py generate-analysis \
  --fact-pack ".../diagnostic-analysis/yuntu-analysis-data.json" \
  --prompt ".../diagnostic-analysis/yuntu-analysis-prompt.md" \
  --output ".../diagnostic-analysis/yuntu-ai-analysis.json"
```

如果当前环境无法直接调用模型，则至少需要在执行流程中明确标记：

```text
model-analysis: pending_manual_model_generation
```

此时不得继续自动渲染最终报告，除非用户明确允许使用程序化兜底分析。

### 验收标准

P0 优化完成后，应满足：

- 执行流程中能明确区分：
  - `programmatic_fallback`
  - `model_generated`
  - `manual_model_generated`
- 最终报告交付时必须说明 `yuntu-ai-analysis.json` 的来源。
- 如果不是模型分析生成，最终状态不能写成“完整模型分析流程完成”。
- 测试需要覆盖：
  - 缺少模型分析 JSON 时不能静默生成报告
  - 程序化兜底必须显式标记
  - 报告数据文件中保留分析来源字段

## 三、P1 优化项：日期口径显式确认

### 当前问题

用户输入：

```text
7.28-8.2
```

执行时按上下文转换为：

```text
2026-07-28 ~ 2026-08-02
```

这个判断本次是正确的，但执行前没有把转换结果作为单独门禁明确输出。

### 优化目标

所有自然语言日期都必须先转成完整日期并展示：

```text
本次将按 2026-07-28 至 2026-08-02 执行。
```

如果存在年份歧义、跨年歧义或用户上下文不足，需要先停下确认。

### 验收标准

- fetch 前必须输出完整起止日期。
- `batch-manifest.json`、`list_context`、`detail-request-params.json` 三处日期必须一致。
- 日期不一致时，不得进入详情和报告阶段。

## 四、P1 优化项：详情阶段进度反馈结构化

### 当前问题

详情接口耗时较长，本次总耗时约 `1488s`。执行过程中虽然持续反馈“正在等待”，但对用户而言信息密度不够。

更有价值的反馈应该是：

```text
详情进度：2/5 成功，0 失败
当前素材：rank 3 / material_id xxx
上一条耗时：268s
```

### 优化目标

详情阶段每次状态反馈都按统一格式输出：

```text
详情进度：成功 N/5，失败 M，当前提交 rank X / material_id Y。
最近成功：material_id Z，耗时 xxxs。
```

如果某条详情 504 或超过合理等待阈值，应立即反馈，而不是继续长时间只说“等待中”。

### 验收标准

- 每条详情成功后反馈 `N/targetTopN`。
- 出现 504 后立即反馈失败素材 ID 和后续候选补位策略。
- 用户能从反馈中判断是否继续等待。

## 五、P1 优化项：旧日期污染检查扩大范围

### 当前问题

本次最终校验只重点检查了是否混入 `2026-07-30`，但历史批次中还出现过：

```text
2026-07-26 ~ 2026-08-01
2026-07-30 ~ 2026-08-05
```

只检查一个旧日期不够完整。

### 优化目标

最终报告交付前应检查所有已知旧日期口径：

```text
2026-07-26
2026-08-01
2026-07-30
2026-08-05
```

同时正向检查目标日期：

```text
2026-07-28
2026-08-02
```

### 验收标准

- HTML、Markdown、final-report-data.json 均通过日期口径检查。
- 如果报告正文不展示日期，也必须在 `final-report-data.json` 中确认事实包 filters 正确。
- 发现旧日期时，报告不得交付。

## 六、P2 优化项：技能说明和连接器参考页读取留痕

### 当前问题

本次执行前读取了 `SKILL.md` 的部分内容，但没有完整重读并留痕所有连接器参考页。

需要读取的参考页包括：

```text
references/platforms/juliang-yt.md
references/connectors/juliang-yt/rpa_conn_juliang_yt_industry_content_rankings_list.md
references/connectors/juliang-yt/rpa_conn_juliang_yt_industry_content_rankings_detail.md
```

本次没有因此产生参数错误，但从“真实完整流程”的可审计性看，需要补齐。

### 优化目标

每次正式执行真实流程前，都生成一个本地读取回执：

```text
skill_read_receipt:
  SKILL.md: read
  platform reference: read
  list connector reference: read
  detail connector reference: read
```

### 验收标准

- 运行目录内保留 `execution-receipt.md` 或等价 JSON。
- 记录技能说明读取状态、参数解释、执行命令摘要和输出目录。

## 七、P2 优化项：运行目录创建校验

### 当前问题

上一轮曾因 shell 单引号导致目录名中出现字面量：

```text
$(date +%H%M%S)
```

本次没有复发，但这是需要固化的执行校验。

### 优化目标

创建目录后必须检查：

- 目录名不包含 `$`
- 目录名不包含 `(`
- 目录名不包含 `)`
- 目录名包含目标日期
- 目录名包含 TopN

### 验收标准

目录名不合格时立即停止，不得继续 fetch。

## 八、建议后的标准流程

优化后的真实完整流程应为：

```text
1. 解析用户输入，显式确认完整日期和品牌名
2. 读取技能说明和连接器参考页，生成读取回执
3. 创建独立运行目录，并校验目录名
4. list-accounts，确认账号和 shop_id
5. fetch，调用列表 RPA 和详情 RPA
6. 列表落盘后反读 list_context
7. 详情阶段结构化汇报 N/targetTopN
8. fetch 成功后校验 manifest
9. prepare-analysis 生成事实包
10. 调用对话模型生成 yuntu-ai-analysis.json
11. render-report 渲染报告
12. 校验日期污染、章节、禁用文案和测试结果
13. 交付报告，并声明分析 JSON 来源
```

## 九、优先级排序

| 优先级 | 优化项 | 原因 |
|---|---|---|
| P0 | 补齐对话模型分析生成 `yuntu-ai-analysis.json` 的正式链路 | 直接影响报告文字质量、分析可信度和“完整流程”定义 |
| P1 | 日期口径显式确认 | 防止自然语言日期歧义 |
| P1 | 详情阶段结构化进度反馈 | 防止用户无法判断是否继续等待 |
| P1 | 旧日期污染检查扩大范围 | 防止历史批次数据混入 |
| P2 | 技能说明和连接器参考页读取留痕 | 提升执行可审计性 |
| P2 | 运行目录创建校验 | 防止 shell 引号导致无效目录 |

## 十、当前建议

下一步建议优先改造 P0：

```text
把 yuntu-ai-analysis.json 的生成从“临时程序化拼接”升级为“明确的模型分析步骤”。
```

如果短期还不能接入自动模型调用，也应该至少加一个强制门禁：

```text
没有模型生成的 yuntu-ai-analysis.json 时，不自动宣称完整流程完成；
除非用户明确允许使用程序化兜底分析。
```
