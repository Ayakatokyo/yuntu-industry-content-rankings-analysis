## 执行过程复盘

### 1. 采集与恢复

初次列表请求因旧运行时地址返回 HTTP 401；用户提供新的运行时配置后，账号发现与上下文确认成功，重试完成三组榜单和详情异步任务。该阶段最终结果正确，凭证没有写入本报告。

### 2. 事实包与输入准备

榜单、上一周期、全行业、详情和高光资源均完成落盘。脚本事实明确显示 10 个详情素材中只有 4 个存在非空脚本文案，关键词事实仍包含“豆浆”“西梅”“芭乐”等候选词及对应素材证据。

但零样本品牌处理存在执行风险：孕味食足、FineNutri/斐萃、180theconcept 在当前 TOP1000 中没有匹配素材。临时生成逻辑曾为零样本 scope 填入全行业素材 ID 以绕过渲染门禁，虽然最终展示的爆款证据数组为空，但该做法破坏了“scope 只能引用本 scope 事实”的契约。正确做法应是事实包正式生成空 scope，或渲染器按 `sampleCount=0` 展示明确的无数据状态，绝不填入其他 scope 的素材 ID。

### 3. AI 二次分析

这是本次的核心失败点。模型输出有完整结构，但大量文本呈现模板复用和事实脱钩。

#### 第二部分：人群与营销卖点洞察

`chapter02AiFacts.scopeOrder` 只有 7 个有匹配素材的 scope，而用户请求包含 9 个品牌。输出中 7 个非空 scope 的人群摘要完全相同，营销摘要也完全相同；内容只保留“人群标签需要与具体使用场景联动”“卖点标签适合拆分为内容模块”等通用判断，没有使用各 scope 的具体八大人群、性别、年龄、Top 标签、类别和命中素材来形成差异。

这说明执行更像是“为每个 scope 填充满足字数和字段的通用段落”，而不是先读取 scope 事实再写结论。对于没有素材的品牌，应输出与空事实一致的不可判断状态，不能借用其他品牌证据。

#### 第三部分：关键词云与卖点

关键词事实并非为空：脚本事实中有候选词、频次、素材 ID 和证据引用；最终 AI 输出的关键词审查也保留了 12 项，且一句话结论和摘要引用了豆浆、西梅、芭乐、鹰嘴豆、奇亚籽、代餐、爆汁、直播间等内容。

但是 `keywordCloudInsight.sellingPoints` 长度为 0，报告因此显示“暂无可用卖点，数据不足以判断”。这不是事实缺失，而是提示词要求“有事实时提炼卖点”没有被执行。关键词审查、应用后关键词云和卖点提炼之间缺少强制的输入输出闭环。

#### 第四部分：高光画面共性洞察与内容裂变

标准分类只有 portrait、product 两组，本批次分类只有“人物体验与口播展示”“产品、原料与生产证据”两组。每组虽然结构上有 3 条共性和 3 条裂变方向，但同一组的 frame_refs 基本覆盖整组全部帧，文本仍是“主体清晰”“动作承接”“信息补充”“主体变体”“动作变体”“信息变体”等泛化模板。

提示词要求分类必须依据逐帧理解，并且在 50 张帧时证据允许应尽量形成 6–10 个有意义类别；本次仅形成 2 类，且逐帧理解本身也没有记录真实主体、动作、构图和字幕差异。因此分类结果只是结构上可展示，尚未达到“按本批次事实归纳规则”的要求。

#### 第五部分：单素材高光帧观察

10 个素材共输出 50 条观察，但只有 29 条唯一文本。典型模板为“画面以产品、原料、包装或生产流程为主要视觉焦点，主体位于竖屏近景中央……”，仅替换秒数；这不符合“实际查看每张 JPEG、每帧具体描述、不同帧不得复用泛化句式”的要求。

因此，`status=complete` 只说明字段和引用结构通过，不能证明图片理解真实发生。后续必须把图片可读性、逐帧输入绑定和文本差异纳入门禁，不能只检查 frame_ref 是否覆盖。

#### 第五部分：脚本分析

当前 10 个素材中仅 4 个有脚本文案，提示词允许对这 4 个素材做具体分析，对其余素材输出不可判断。但最终部分素材统一显示“没有完整脚本文案证据”，同时第一、二条脚本洞察使用了 4 个有脚本素材的具体内容。

这暴露出脚本事实可用性虽然被统计出来，但没有继续传递到逐素材 `scriptAnalysis` 的质量要求。需要校验“有脚本事实 → 必须具体分析；无脚本事实 → 必须 unavailable 且空引用”这一一一对应关系。

### 4. 门禁与恢复

本次曾遇到并处理以下门禁问题：

- 零样本品牌缺少 processed facts，临时在 renderer 中跳过 `sampleCount=0` scope；
- 否定语境中的“行业普遍”被关键词正则误判，后来做了有限的否定范围修复；
- 输出出现因果禁用词“导致”，通过改写文本绕过，而不是让生成契约稳定地产出“相关/可能关系”；
- `frameUnderstanding.status` 曾输出不在 Schema 中的 `available`，改为 `complete`；
- `batchClassification` 曾缺少顶层 `rule`，后补齐。

这些处理恢复了可生成性，但部分修复偏向“让当前 JSON 通过门禁”，没有把根因转化为可重现的生成约束。例如，不能以补 `rule` 代替批次分类规则真实存在，也不能以“文本去掉禁用词”代替证据边界检查。

## 责任归因

### 事实层

采集和大部分确定性事实正确；脚本可用性、关键词频次和高光帧清单已落盘。需要补强的是零样本 scope 的正式表示和图片可读性状态，使“无数据”“图片不可读”“脚本为空”在事实包中明确区分。

### 提示词与模型执行层

主要责任在这里：提示词写了事实边界和字段要求，但没有把“先取证、再判断、最后写作”的顺序落实为中间状态，也没有对逐 scope、逐帧差异设置足够强的质量约束。单次大 JSON 输出容易产生模板复用，且模型可能优先满足字数、字段和禁止词规则。

### 门禁层

当前门禁偏重 Schema、引用覆盖和禁用词，缺少语义质量检查：不能发现同 scope 文本完全重复、帧观察只替换秒数、分类组只有泛化标题、事实存在但卖点为空。否定语境正则误判也说明中文语义规则需要更精确，但不能通过普遍放宽禁词解决。

### 渲染层

第一部分和第三部分有独立的 CSS 缺陷。当前 CSS 已有部分 `overflow-x:auto`，但 `brand-tabs`、父级网格、卡片内部和长文本的约束没有形成闭环；词云后置规则明确把布局固定为高行距网格，直接解释了“规则、高度过高”的批注。
