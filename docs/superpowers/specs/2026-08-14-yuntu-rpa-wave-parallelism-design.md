# 云图详情 RPA 波次并行与高光帧流水线设计

## 目标

将详情 RPA 从串行调用改为固定三并发的波次调度。每条详情成功落盘后，立即启动该素材的视频下载和高光帧截图；一整个波次的 RPA 与高光帧任务都进入终态后，才允许提交下一波候选素材。

该改造缩短详情 RPA 的墙钟时间，同时保持现有输出目录、筛选契约、同组 TOP 补位、失败记录和断点续跑语义。

## 范围

- `fetch` 的详情阶段采用两个独立的 `ThreadPoolExecutor`：RPA 并发数固定为 3，高光帧后处理并发数固定为 3。
- 同一波次最多提交 3 个候选素材；详情成功后立即将高光帧处理交给后处理线程池。
- 下一波仅在当前波次每个素材均已完成详情处理，并且成功详情的高光帧任务也已完成后启动。
- 高光帧失败为非阻断终态：记录帧失败原因，允许波次收口和下一波开始，不触发新的详情 RPA 补位。
- 高光帧结果在详情阶段写入 `highlights/<material_id>/` 与 `highlights-manifest.json`。`prepare-analysis` 复用已落盘帧，只对中断后缺失的帧补处理。
- `batch-manifest.json` 与 `run-summary.json` 增加可观察的波次/后处理状态和耗时，不在其中复制大体积详情 records。

## 非目标

- 不更改列表 RPA；列表仍只请求一次且串行完成。
- 不变更 RPA 网关协议、连接器元数据、鉴权方式或服务端超时。
- 不把高光帧失败视为详情 RPA 失败，也不以帧失败触发候选补位。
- 不改变 `retry-failed` 和 `retry-unresolved` 的授权语义；未确认的已提交详情仍不会自动重发。
- 不对单个视频内的多张 JPEG 再做并行 FFmpeg 截图，避免将每素材最多六个子进程放大为不可控负载。

## 调度模型

1. 复用或请求列表，并完成列表规范化和筛选上下文校验。
2. 根据 `candidateTopN` 和每个选择组的 `targetTopN` 构建候选序列，恢复已持久化的详情和高光帧状态。
3. 选取当前组仍需的最多三个候选组成一个波次，并在 RPA 线程池中并发调用详情连接器。
4. 某条详情 RPA 返回后，在主调度线程完成 CSV/JSON 落盘、规范化和详情记录原子写入；成功记录随后提交至高光帧线程池。
5. 主调度线程持续回收详情与高光帧 future，并在每次状态变化后原子写入 manifest 与 run summary。
6. 当前波次的所有详情和后处理 future 均进入成功或失败终态后，才计算同组缺口并发起下一波。达到目标的组不再提交候选。
7. 全部波次结束后，按既有规则生成 `top-materials-rpa-ready.json`，并以详情选中/拒绝状态确定批次 `success` 或 `partial`。

## 状态与恢复

详情完成前中断的已提交项继续归入 `unresolvedMaterials`，常规续跑不重发。详情记录已原子落盘但后处理未完成时，续跑不重发详情，只重新排入缺失高光帧的后处理队列。

后处理状态是独立于详情选中状态的附加信息。详情成功即保留为 `selectedMaterials`；高光帧异常写入 `highlights-manifest.json` 和素材后处理状态，最终事实包沿用现有 `available=false` 与 `failure_reason` 表达数据缺失。

所有 manifest 与 summary 写入只能由主调度线程执行。工作线程仅返回结果，避免并发写 JSON 造成文件损坏或状态覆盖。

## 模块边界

- `scripts/yuntu_batch.py`：波次调度、详情 future 回收、详情持久化、状态检查点和候选补位。
- `scripts/yuntu_highlights.py`：提供单素材的可恢复高光帧处理函数，以及汇总 manifest 的写入/读取能力；保留现有帧选择、下载上限与原子 JPEG 发布规则。
- `scripts/yuntu_analysis.py`：不再总是串行生成全部帧；读取已生成帧并仅补处理缺失项，然后组装事实包。
- `scripts/rpa_connector.py`：保持 CLI 契约；可在帮助文本中说明固定的三素材波次。

## 验收条件

1. 首个波次恰好可并发提交三条详情 RPA，且不会在任一波次未收口时提交第四条。
2. 某一详情成功持久化后，其高光帧任务可在同波次其余 RPA 仍运行时开始。
3. 下一波在上波高光帧成功、失败或复用完成前均不得开始。
4. 高光帧失败记录为非阻断终态，不造成额外详情 RPA 调用。
5. 同组目标已满足时，该组不会继续提交；失败详情仍可使用同组候选在后续波次补位。
6. 详情已持久化、高光帧未完成的中断批次续跑时，不重复调用详情 RPA。
7. 既有串行调用、列表失败、详情失败、恢复和报告事实包测试继续通过；新增并发测试不依赖真实网关或 FFmpeg。
